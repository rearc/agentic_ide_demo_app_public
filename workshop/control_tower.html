Workshop · Block 13

lab: the control tower

Done looks like

A branch you are happy with and can explain end to end without the agent there: you know what was decided, and why. Not every task finished; a branch you understand. If something goes sideways, don't worry: message a trainer and we'll help fix it.

Make it yours

Bring an idea worth splitting into tasks. A very complex card; a playable game on one of the bigger widgets; a set of cards that together serve one purpose, like a live tracker for several sports with each card made for its sport. Don't be scared to take risks: it's way more fun to try something you're not sure will work. Pick something worth this pattern: changing the CSS in a few places doesn't need a control tower; building a theme library does.

Or take the themes change

The option we know works end to end, the one the trainer showed you. Use this as your change in step 2:

Copy and paste
Add themes to the dashboard. A theme library of whole palettes: each palette sets every region of the app (page background, panels, borders, text, header accent, card colours, status colours). Graphite, today's look, stays the default. Five new palettes join it, researched and proposed for me to choose from, not invented on the spot. A picker in the header switches palette, each profile remembers its palette, and a Themes tab in the library drawer shows every palette as a mini dashboard. Last, a high-contrast palette, added the way any future palette would be added, so we learn what adding one takes.
Keep in mind

  • Usage: keep an eye on your usage, and be realistic about what you can get done, or make real progress on, in the time you have. Stay on Opus in every session; if usage gets tight, scope down rather than switch models. Biting off more than you can chew is fine: there's no failing here.
  • Data: make sure a data source won't cost money. You can always start from mock data (the agent can build it) and plug the real source in later.
  • Too big? Run it by a trainer, who'll help you take on a slice that the rest can build on.
Where

The CLI in VS Code's integrated terminal, one terminal per session, or the Claude Code extension, one conversation per session (switch between them with the conversation selector). Several sessions run at once, so keep each one's name in view.

  1. 1. A fresh clone

    Stop Day 1's dev servers first (Ctrl+C in their terminals), so this clone's app gets the default ports and you don't test yesterday's app by mistake.

    Clone the lab's starting point into a new folder, next to yesterday's:

    Copy and paste
    git clone -b lab/start https://github.com/rearc/agentic_ide_demo_app_public.git control-tower-lab

    Set it up as on Day 1 (its README, "Setup"): cp .env.example .env in the root; in backend/, the venv, pip install -r requirements-dev.txt, flask --app run.py db upgrade, python seed.py, python run.py; in frontend/, npm install, npm run dev. The installs are quick: your caches are warm. Trouble getting the app to start? Ask Claude for help in that folder.

    Open the new folder in VS Code. Claude Code asks once whether you trust it (yes), and whether to enable the repo's two MCP servers (enable both, as on Day 1). Check the mode says auto (Shift+Tab in the CLI; the mode indicator in the extension). In the extension, use Claude Code 2.1.300 or later.

    Make a branch for your change, named for it:

    Copy and paste
    git switch -c <change>

  2. 2. Split it into tasks

    In the CLI: in a terminal in your control-tower-lab folder:

    Copy and paste
    claude -n decompose

    In the extension: start a new conversation from the conversation selector; rename it decompose once it has named itself.

    Then, with your change in a few sentences:

    Copy and paste
    /decompose-to-specs <your change>

    It grills you, as on Day 1, then splits the work. Answer each round; "go with your recommendations" is fine for details, but this is your design, so think about the parts that matter to you.

    You should see: a table of tasks, each human-in-the-loop (built with you) or delegated (built by a worker on its own), what each depends on, and what runs in parallel. Change what you'd split differently. When it's right:

    Copy and paste
    Looks right, commit it.

    You should see: specs/<change>/ with spec.md (its Interfaces section fixes the names tasks share), one task spec per task in tasks/, and plan.md; one commit, Plan: <change> split into tasks.

  3. 3. Start the main session

    In the CLI: /clear in the decompose session. In the extension: start a new conversation from the conversation selector.

    Then:

    Copy and paste
    /main-session specs/<change>/

    You should see: what's done, what can start now, and an offer to start the delegated tasks that are unblocked, with the commands for each.

  4. 4. Start workers

    For each delegated task you want started, the main session gives you the commands.

    In the CLI: a new terminal, opened in your control-tower-lab folder:

    Copy and paste
    claude -n <task>

    In the extension: start a new conversation from the conversation selector; rename it to the task once it has named itself.

    Then, in either:

    Copy and paste
    /worker-session specs/<change>/tasks/NN-<task>.md

    Each worker moves itself into its own worktree (.claude/worktrees/<task>), sets up its own copy of the app on its own ports, writes its plan into its task spec and waits for your go. Read it, then go. Tell the main session which workers you started.

    Start as many workers as you can keep up with: each one's work comes back to you for review.

  5. 5. Build the human-in-the-loop task with the main session

    It writes its plan into the task spec and waits for your go; then it builds test-first and comes back to you at decisions the specs don't settle and when there's something to look at in the app.

    Now and then, switch to your workers. If one asks you something, answer it there, then come back.

  6. 6. Bring the handoffs back

    When your task is done, that's the time to bring finished workers' handoffs. A worker's last message is its handoff: copy it (in the extension, "Copy response" on the message), paste it into the main session. One at a time.

    You should see: a review summary: what the task did, decisions it made alone, what it couldn't check, what to look at. Then you decide:

    • Request changes: the main session writes the message; paste it into the worker. It fixes and hands off again.
    • Merge: it merges, resolves any merge conflict (normal when workers run side by side; check the result against spec.md's Interfaces), runs the checks and says what can start next.

  7. 7. The next iteration

    Between iterations (a task done, its handoffs merged), the main session may suggest a fresh one. Take it. CLI: /exit, then claude -n <next-task>-main in the same terminal. Extension: start a new conversation from the conversation selector and rename it. Then /main-session specs/<change>/. The files carry everything.

    Repeat steps 4 to 7.

  8. 8. The end

    When every task is merged or done, the main session runs every check, /code-review lab/start...HEAD and each acceptance criterion; you pick which findings to fix, and each fix is one more task. Then cleanup. CLI: first /exit each worker (on its dialog, choose Keep worktree: the main session removes them), then tell the main session to clean up. Extension: tell the main session to clean up; if it says a worker still holds its worktree, ask it what to do.

    Optional, the next logical step: a pull request to your own GitHub copy. Or merge your branch locally; at work, this is where you'd open a pull request and go through your team's normal review.

What you'll meet

  • A question card with previews: if a number key doesn't pick, use the arrows and Enter.
  • Closing a session that started dev servers: "Background work is running": choose Exit and stop tasks.
  • A worktree session's exit dialog: always Keep worktree: your work stays until the main session merges it and cleans up.
  • In the extension: name a file in your prompt rather than selecting code in a worker's files (it only sends the path).
Rather watch

The trainer runs a control tower of their own on screen in the main room. Follow it there, or pair with someone and share one screen. Solo is encouraged: being in control of it yourself is the fun part.
