Workshop · Block 9

Capstone: one hard card, end to end

Where

The CLI in VS Code's integrated terminal (claude in the workshop repo folder) or the Claude Code extension; the board in your browser at http://localhost:5173, or the port npm run dev prints if 5173 is in use. Trouble getting the app to start? Ask Claude for help.

Done looks like

A target, not a test. Aim for: the check named before building, and its output shown; your card seen working in the app; code-review run against your feature file, every finding fixed or answered; every line one you can explain; committed on your own branch. Get as far as you can; not finishing is fine.

Make it yours

The menu is a starting point and the steps are one good path, not rules. Bring your own idea and work it your own way. This board is an app of apps: one card already draws a 3D globe with d3.js and tracks the ISS live. A Flappy Bird clone, Snake, a Wordle? Go for it.

One limit, one feature

Pick something a single feature file can hold: one grill settles it, one spec describes it, one fresh session builds it. If the grill keeps finding whole new pieces (accounts, a leaderboard, a level editor), you have several features. Ask Is this one feature or several? If several, which should I build first? and build the first one today. The rest can wait.

Before you start

The workshop repo is on main with nothing uncommitted (git status). Make a branch named after your card:

Copy and paste
git switch -c capstone-<card>

Both servers are running (the repo's README, "Setup": python run.py in backend/, npm run dev in frontend/) and the board is open. The build adds your card to your board through the seed; python seed.py --reset in backend/ puts back the default board if you need it (it also clears your todos).

Rather watch

The trainer builds a card of their own during the lab, on screen in the main room. Follow it there, or pair with someone and share one screen.

  1. 1. Pick a card

    Choose from the menu for ideas, or bring your own. Know its type: it decides how much backend work there is.

    Type Card Data from What makes it worth a grill
    Static World clock the browser (Intl) which zones and where they are set; daylight saving; small sizes
    Static Countdown to a date nothing where the date is set; a date that has passed; time zones
    Static Tic-tac-toe against a simple computer player nothing the player's rules, written as criteria a test can check
    Data Hacker News top stories hacker-news.firebaseio.com one request per story; how many; the 5 second timeout across several calls
    Data Earthquakes near my city the USGS GeoJSON feed radius and magnitude cut-offs; reusing the app's geocoding; "none today"
    Data Exchange rates Frankfurter (api.frankfurter.dev) base currency and which pairs; change since yesterday needs a second call
    Data Next public holiday Nager.Date (date.nager.at) country as config; the countdown; a holiday today
    Data US weather alerts api.weather.gov US only; it wants a User-Agent header; "no alerts" is the usual state
    Data Trivia Open Trivia DB (opentdb.com) HTML-encoded text; a score the card keeps; a rate limit per address
    Data, key Stock quote Alpha Vantage (free key) the key goes in .env; a daily request cap
    Stateful Habit tracker its own table streaks across days; when a day ends; the migration
    Stateful Quick links its own table ordering; checking a URL; the migration
    Stateful Standup log its own table one entry a day; editing yesterday's; the migration

    Already on the board, so not on the menu: weather, daily quote, space photo, daylight, ISS globe, timer, moon, todos, and the trainer's air quality card.

    Want a sure finish today, pick static. Want the whole loop, data. Want the hard part, stateful: only a stateful card needs a database migration.

  2. 2. Understand the code it touches

    Fill in your card and its type:

    Copy and paste
    I want to add a <card> card. Before we plan anything: how does a <type> card work here, end to end, from the service to the card on the board, and what can a <card> card reuse?

    You should see: the files your card will touch, named, and what it can reuse. Ask about anything you could not explain to a teammate before you go on.

  3. 3. Grill it into a feature file

    Copy and paste
    Grill me on this card.

    Answer each round. The trainer said yes to most recommendations for time; this is your card, so think about yours. When a round runs long:

    Copy and paste
    For the rest, go with your recommendations and show me the summary.

    When the summary is right:

    Copy and paste
    Yes, that's our shared understanding. Write it to specs/<card>.md as a feature file.

    You should see: specs/<card>.md with the problem, the decisions and why, at least three acceptance criteria each naming its check, what is in and out of scope, the parts of the app, a progress checklist and a "Resume here" line at the top.

  4. 4. One design

    Copy and paste
    Show me one look for this card as a temporary HTML file in this repo, and record it in the feature file.

    Open the file in your browser. Not right? Say what to change, or ask for a very different one.

    You should see: a page showing your card; the feature file names the look chosen.

  5. 5. Restart from the file: it builds

    Copy and paste
    Update the feature file: progress so far, what you learned about the code, and a resume line a fresh session can start from.

    Then /clear. In the extension, click the + button to open a new thread instead: it does the same thing. Then send:

    Copy and paste
    Read specs/<card>.md and carry on from its resume line.

    That session has never seen your conversation. Open specs/<card>.md in the editor and watch its checklist tick while it works.

    You should see: it starts at the first unticked box, writes a test before the code, and runs every check with its output shown.

  6. 6. See it in the app

    Open the board and find your card (Edit board, then Library, if it is not on the board). Use it. Resize it, down to the smallest size the board allows. If the build did not run the check-ui skill, ask for it.

  7. 7. Prove a test can fail

    Pick the test you trust least:

    Copy and paste
    Show me this test fails without your change.

    You should see: it goes red, for the reason the test is about, then green again. Red for another reason (an import error, a typo)? Ask Is that the right reason for it to fail?

  8. 8. Review

    Copy and paste
    Review this branch against specs/<card>.md with the code-review skill.
    Copy and paste
    Fix what you agree with, tell me what you don't, then show me the diff of the test files.

    In the test diff, look for a test that was changed to pass rather than code that was fixed. Then open any file you could not explain line by line:

    Copy and paste
    Walk me through <file>: why is it written this way?

  9. 9. Commit

    Copy and paste
    Commit it.

    You should see: one commit on your capstone-<card> branch. Delete the temporary design file first if it is still there, unless you want to keep it.

When stuck

Block 8's escapes. Ask "what could cause this?" instead of "fix this". Check your own assumptions. Three failed fixes means question the design. Say "stop guessing". For a second opinion, a fresh session or a read-only subagent that has not seen your theory. Still stuck: post in chat what you are stuck on, and a trainer will come to you.

Before you stop

Wherever you are, even mid-step, send step 5's "Update the feature file" prompt, then commit it (Commit the feature file.), so it says where you got to.

Traps by card type

Type Watch for
Every card The temporary design file lands inside frontend/src, where lint checks it: delete it before you commit. The end-to-end suite fails until your card has a place on its test board and mocked data. The agent may git stash on its own. The seed runs on your own board.
Static It feels done fast: check it at its seeded size and at the smallest size (the timer's lesson from Blocks 6 and 7). Its settings reset on reload unless you decided otherwise in the grill. It needs no backend: stop the agent if it adds one.
Data Config values reach the service as strings. A fallback keeps every key a success has. The data route's test fails until it has a case for your source, and tests block any request they did not mock. A rate limit is shared by everyone behind one office address. A key goes in .env, which Claude may not read: it tells you to add the key yourself, and carries on.
Stateful The migration is the hard part: foreign keys are enforced, so it says what happens on delete, and the migration tests must pass. Decide in the grill whether its data is per profile or shared: a card's settings (config) are shared by every profile.
