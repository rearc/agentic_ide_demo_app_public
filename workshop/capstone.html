Workshop · Block 9

Capstone: one hard card, end to end

Where

The CLI in VS Code's integrated terminal (claude in the workshop repo folder) or the Claude Code extension; the board in your browser at http://localhost:5173, or the port npm run dev prints if 5173 is in use. Trouble getting the app to start? Ask Claude for help.

Done looks like

A target, not a test. Aim for: the check named before building, and its output shown; your card seen working in the app; /code-review run and each acceptance criterion in your spec checked, every finding fixed or answered; every line one you can explain; committed on your own branch. Get as far as you can; not finishing is fine.

Make it yours

The menu is a starting point and the steps are one good path, not rules. Bring your own idea and work it your own way. This board is an app of apps: one card already draws a 3D globe with d3.js and tracks the ISS live. A Flappy Bird clone, Snake, a Wordle? Go for it.

One limit, one feature

Pick something one spec can hold: one grill settles it, one spec describes it, one plan builds it. If the grill keeps finding whole new pieces (accounts, a leaderboard, a level editor), you have several features. Ask Is this one feature or several? If several, which should I build first? and build the first one today. The rest can wait.

Before you start

Pick a short name for your card, lowercase with hyphens, like world-clock, and use it wherever <card> appears below (the branch, the specs/<card>/ folder, the prompts). The workshop repo is on main with nothing uncommitted (git status). Make a branch named after your card:

Copy and paste
git switch -c capstone-<card>

Both servers are running (the repo's README, "Setup": python run.py in backend/, npm run dev in frontend/) and the board is open. The build adds your card to your board through the seed; python seed.py --reset in backend/ puts back the default board if you need it (it also clears your todos).

Rather watch

The trainer builds a card of their own during the lab, on screen in the main room. Follow it there, or pair with someone and share one screen.

  1. 1. Pick a card

    Choose from the menu for ideas, or bring your own. Know its type: it decides how much backend work there is.

    Type Card Data from What makes it worth a grill
    Static World clock the browser (Intl) which zones and where they are set; daylight saving; small sizes
    Static Countdown to a date nothing where the date is set; a date that has passed; time zones
    Static Tic-tac-toe against a simple computer player nothing the player's rules, written as criteria a test can check
    Data Hacker News top stories hacker-news.firebaseio.com one request per story; how many; the 5 second timeout across several calls
    Data Earthquakes near my city the USGS GeoJSON feed radius and magnitude cut-offs; reusing the app's geocoding; "none today"
    Data Exchange rates Frankfurter (api.frankfurter.dev) base currency and which pairs; change since yesterday needs a second call
    Data Next public holiday Nager.Date (date.nager.at) country as config; the countdown; a holiday today
    Data US weather alerts api.weather.gov US only; it wants a User-Agent header; "no alerts" is the usual state
    Data Trivia Open Trivia DB (opentdb.com) HTML-encoded text; a score the card keeps; a rate limit per address
    Data, key Stock quote Alpha Vantage (free key) the key goes in .env; a daily request cap
    Stateful Habit tracker its own table streaks across days; when a day ends; the migration
    Stateful Quick links its own table ordering; checking a URL; the migration
    Stateful Standup log its own table one entry a day; editing yesterday's; the migration

    Already on the board, so not on the menu: weather, daily quote, space photo, daylight, ISS globe, timer, moon, todos, and the trainer's air quality card.

    Want a sure finish today, pick static. Want the whole loop, data. Want the hard part, stateful: only a stateful card needs a database migration.

  2. 2. Understand the code it touches

    Fill in your card and its type:

    Copy and paste
    I want to add a <card> card. Before we plan anything: how does a <type> card work here, end to end, from the service to the card on the board, and what can a <card> card reuse?

    You should see: the files your card will touch, named, and what it can reuse. Ask about anything you could not explain to a teammate before you go on.

  3. 3. Grill it into a spec

    Copy and paste
    Grill me on this card.

    Claude asks in rounds: numbered questions (Q1, Q2, ...), each with its recommended answer. Reply to each by number in one message, for example Q1 yes, Q2 only Europe/Berlin and Asia/Tokyo, Q3 no; "yes" takes the recommendation. If it writes a spec without asking you anything, say Use the grilling skill. Think about each one: this is your card. Keep answering rounds until it shows a summary of what you agreed. When the summary is right:

    Copy and paste
    Yes, that's our shared understanding. Write the spec to specs/<card>/spec.md.

    You should see: specs/<card>/spec.md with the problem, the decisions and why, at least three acceptance criteria each naming its check, what is in and out of scope, the parts of the app, and any open questions. The spec is what you're building and how you'll know it's done; it changes only when you decide something.

  4. 4. One design

    Copy and paste
    Show me one look for this card as a temporary HTML file in specs/<card>/, and record the look chosen in the spec's decisions.

    Open it: in VS Code's Explorer, right-click the HTML file in specs/<card>/ and choose "Open in integrated browser" (or open the file in any browser). Not right? Say what to change, or ask for a very different one.

    You should see: a page showing your card; the spec's decisions name the look chosen.

  5. 5. Plan it with Claude

    1. Ask for a plan. Switch to Plan Mode (Shift+Tab until the status line says plan mode on), then send:
      Copy and paste
      Plan the build from specs/<card>/spec.md. Save the plan beside the spec.
    2. Work the plan with it. This is a back and forth, not one message. The plan is what gets built next, by a session that never saw this conversation, so this is your chance to be in the loop on what it will do. Answer its questions, then read the plan and critique it: ask why for any step you don't follow, push back on anything the spec doesn't ask for, and check each step names how it will be checked. Write these in your own words, about your plan; the two below only show the kind of thing to ask:
      Example only: write your own
      Which step is the riskiest, and how will we know it worked?
      Example only: write your own
      Step 3 isn't in the spec. Drop it, or tell me why we need it.
      Take your time here; it is cheaper to fix a plan than a build. Keep going until you would hand this plan to a teammate.
    3. Approve it. When the plan is right, Claude Code shows the approval card: the prompt at the end of Plan Mode that asks whether to go ahead with the plan, and how. Choose Yes, clear context and use auto mode: the build starts in a fresh session that has never seen your conversation, with only the plan, and in Auto mode, so it works without asking before each edit. In the extension, if the approval has no "clear context" option: approve, and once specs/<card>/plan.md exists, click the + button to open a new thread and send Read specs/<card>/ and carry on from the plan's Status.

  6. 6. Build it with Claude

    The plan is Claude's best guess at a route, written before it touched the code. The build will meet things the plan did not see: a test that will not pass, an API that answers differently, a file that is not where it expected. Stay in this thread while it works; you are the one who notices when it drifts.

    Read what it says as it goes, not only the end. Step in when (Esc in the CLI, or the stop button in the extension, then type):

    • it tries the same fix again and again;
    • it changes course from the plan without saying why;
    • it reaches for something the spec ruled out;
    • it asks you something, or stops to wait.

    Say it in your own words, about what you see. Two examples of the kind of thing:

    Example only: write your own
    Stop. That's the same fix as before. What do you think is actually wrong?
    Example only: write your own
    That isn't in the plan. Why the change? If we keep it, update the plan.

    You don't need to track the plan yourself: it updates as the build goes, ticking each step once its check passes, so specs/<card>/plan.md always shows where things stand.

    Is it done? When Claude stops, open plan.md: done means every box is ticked and each check's output was shown. Stopped with boxes still open? Send Carry on from the plan's Status.

    You should see: specs/<card>/plan.md with a Status section near the top (where it stands, and a checklist where each step names its check); the build starts at the first unticked box, writes a test before the code, and ticks each box only after its check passes, with the output shown.

  7. 7. See it in the app

    Open the board and find your card (Edit board, then Library, if it is not on the board). Not in the Library either? The seed adds new cards to the board, and the build may not have run it: ask Did the seed run? If not, run it.

    Then try it against your spec: take each acceptance criterion and check it on the board yourself. Resize the card, down to the smallest size the board allows. Then ask Did you run the check-ui skill on my card? If not, run it now.

  8. 8. Prove a test can fail

    A passing test is only worth something if it would fail when the code is wrong. Claude wrote these tests during the build, so check at least one.

    1. List the tests.
      Copy and paste
      List the tests you added for this card, with one line on what each one checks.
    2. Pick one you trust least: one that guards behaviour you care about, or one you can't match to an acceptance criterion in your spec.
    3. Break the code it tests, on purpose. Fill in the test's name:
      Copy and paste
      Show me <test name> fails without your change: take out the code it tests, run the test, then put the code back and run it again.
      You should see: red first, with a failure about the behaviour the test checks; then green once the code is back.
    4. Check everything is back. Run git status and git stash list yourself. Your files should be as they were before step 3, and if Claude used git stash to take the code out, the stash list should be empty again.
    5. If it didn't go as expected:
      • Red for another reason (an import error, a typo)? Ask Is that the right reason for it to fail?
      • Still green with the code taken out? The test doesn't check your code. Ask Claude to change the test so it would catch the code being broken, then try step 3 again.

  9. 9. Review

    Claude Code's own review, for bugs in everything this branch changed:

    Copy and paste
    /code-review

    It runs in the background and can take a few minutes; its findings arrive as a message in your conversation. It doesn't know your spec, so check that separately while you wait:

    Copy and paste
    Check each acceptance criterion in specs/<card>/spec.md against this branch, by the check it names, and show each check's output.

    Once the review's findings have arrived (not before), send:

    Copy and paste
    Fix what you agree with from both, tell me what you don't, then show me the diff of the test files.

    In the test diff, look for a test that was changed to pass rather than code that was fixed. Then open any file you could not explain line by line:

    Copy and paste
    Walk me through <file>: why is it written this way?

  10. 10. Commit, then back to main

    1. Delete the temporary design file from specs/<card>/, unless you want to keep it.

    2. Commit:

      Copy and paste
      Commit it.

    3. Check it: run git log --oneline -1 and git status yourself.

      You should see: one new commit on your capstone-<card> branch, holding your spec, your plan and the code, and git status with nothing left to commit. Plan Mode's own copy in plans/ is a draft and stays out.

    4. Back to main: git switch main. Your card stays on capstone-<card>, so you can carry on from it later.

When stuck

Block 8's escapes. Ask "what could cause this?" instead of "fix this". Check your own assumptions. Three failed fixes means question the design. Say "stop guessing". For a second opinion, a fresh session or a read-only subagent that has not seen your theory. Still stuck: post in chat what you are stuck on, and a trainer will come to you.

Before you stop

Wherever you are, even mid-step, send Update the Status in specs/<card>/plan.md: what's done and what's next., then Commit the spec and the plan., so they say where you got to. To pick it up later: /clear (or the + button in the extension), then Read specs/<card>/ and carry on from the plan's Status.

Type Watch for
Every card The temporary design file belongs in your spec folder; if it lands inside frontend/src anyway, lint checks it: delete it before you commit, or leave it out of the commit. The end-to-end suite fails until your card has a place on its test board and mocked data. The agent may git stash on its own. The seed runs on your own board.
Static It feels done fast: check it at its seeded size and at the smallest size (the timer's lesson from Blocks 6 and 7). Its settings reset on reload unless you decided otherwise in the grill. It needs no backend: stop the agent if it adds one.
