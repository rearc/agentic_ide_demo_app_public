Workshop · Block 5

Primitives breakout: a skill, a rule and an MCP tool

Where

The CLI in VS Code's integrated terminal (claude in the workshop repo folder), as in the try-its. Create the files in VS Code's editor.

Before you start

The workshop repo is open on main with no uncommitted changes. Make a branch:

Copy and paste
git switch -c primitives

You do not need to restart Claude Code after adding a file: a skill or a rule added while a session is open works on the next prompt.

Do not

Ask Claude to write these for you. Type or paste them yourself; use Claude to test them and to critique them.

  1. 1. A skill: explain-file

    A skill is a folder with a SKILL.md in it. Its description is loaded at the start of every session; its body only when the skill is used. The description is how Claude decides to use it without being told.

    1. Create .claude/skills/explain-file/SKILL.md with this content, and write the description line yourself: one sentence saying what it does, then "Use when …" with the words someone would actually type.
      File content (markdown)
      ---
name: explain-file
description: <what it does>. Use when <how people ask for it>.
---

# Explain a file

Read the file, then answer in exactly three lines and nothing else:

**Purpose:** what the file does, in one sentence.
**Used by:** the files or commands that use it.
**Watch out:** one thing that would surprise someone changing it.
    2. Use it by name: send /explain-file backend/run.py. You get the three lines. There is no Skill(...) line: typed by name, the skill's text goes straight into your message.
    3. Now without its name: send What does backend/run.py do? If the skill fired you see Skill(explain-file) and "Successfully loaded skill" above the answer, and the answer is the three lines.
    4. If it did not fire, ask Claude, not to fix it but to critique it:
      Copy and paste
      Critique the description in .claude/skills/explain-file/SKILL.md: would it make you use this skill for "What does backend/run.py do?" Suggest a better one. Don't edit the file.
      Change the description yourself, then try step 3 again.

  2. 2. A rule: open the test with the service

    A rule in .claude/rules/ is an instruction for Claude. With paths: at the top it loads only when Claude reads a matching file, so it costs nothing until it matters.

    1. Create .claude/rules/services-tests.md:
      File content (markdown)
      ---
paths:
  - "backend/app/services/**"
---

# A service is not explained without its test

Whenever you read or change a service, open `backend/tests/test_services_<name>.py` too and name the test that covers its fallback path. If none does, say so before anything else.
    2. See it load: send Read backend/app/services/quotes.py and explain what it does. Look for Loaded .claude/rules/services-tests.md under the read, then a second read, of backend/tests/test_services_quotes.py, that you did not ask for, and the name of the test that covers the fallback.

  3. 3. An MCP tool: add one to the local server

    An MCP server is a separate program that gives Claude tools. The repo's random-tools server is a short Python file you can read; a tool is a function, its docstring is the description Claude sees, and its type hints become the arguments.

    1. Open mcp-servers/random-tools-mcp/server.py. Add this tool below roll_die, and write the docstring yourself: one sentence saying what it does.
      Copy and paste
      @mcp.tool()
def pick_one(options: list[str]) -> str:
    """<what it does>"""
    return random.choice(options)
    2. Reload the server: a running server does not see your edit. Run /mcp, choose random-tools, then Reconnect.
    3. See it listed: in the same /mcp panel, random-tools now lists three tools, pick_one among them.
    4. See Claude use it: send Use random-tools to pick one of: tacos, ramen, pizza. You see the pick_one call with your three options, then the answer.

  4. 4. Look around, commit, then back to main

    1. Run /context and find explain-file under Skills: only its description costs context until it is used. Look for your rule: it is not listed, and /memory does not list it either. The Loaded … line was your proof that it loaded.
    2. Commit them: git add .claude mcp-servers && git status (check it lists only your three files), then git commit -m "Add explain-file skill, services-tests rule and pick_one tool".
    3. Switch back to main: git switch main. Your work stays on the primitives branch; the rest of the day starts from main.
Done looks like

The skill fired without its name, the rule showed as loaded, Claude called your new tool, and you are back on main; or you can say why one of them did not.

Finished early? On the primitives branch (git switch primitives), write a second skill of your own: something you would use at work, or one of roast-my-code (a light, useful roast of a file), explain-like-im-new (one concept, no jargon), pr-description (from the branch's diff). Then trade with a neighbour in chat: can they make it fire without knowing its name?
